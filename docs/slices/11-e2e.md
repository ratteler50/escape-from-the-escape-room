# Slice 11 — Playwright end-to-end tests in CI

**Status:** built, agent-verified · awaiting PR, CI, and developer review · **Milestone:** M2 (Phase C, tooling) · **Branch:** `slice-11-e2e`

Runs in parallel with slice 10 (cutscenes), in its own session. To keep the two from colliding, this
slice touches nothing in `src/core/`, `src/view/`, `docs/design.md`, or the other slice docs, and in
`src/content/` only the always-winnable test's search (moved into a module, below). Anything those
files should say is noted at the bottom of this doc instead.

## Why

Every test so far runs the headless core. Nothing automated checks the Phaser view: that a hotspot
can actually be clicked, that the verb coin opens where it should, that the inventory, dialogue
panel, room change, and end card work together, that a save survives a reload. Those have only been
checked by hand (the agent's and your play-tests), and Copilot's PR reviews keep pointing it out.

Game-dev note: a Phaser game draws everything onto one `<canvas>`. There are no DOM buttons for a
browser test to find by text, so the test asks the running game where things are (through the
`window.__game` hook) and clicks those screen coordinates with a real mouse, the way a player would.

## Spec

### The hook in production builds

1. `src/main.ts` exposes `window.__game` when the build is a dev build **or** the page URL has an
   `?e2e` flag (`/?e2e`). Without the flag a production build behaves exactly as today. Anyone could
   add the flag on the live site and poke at the game from the console; that's harmless for a
   single-player game with no accounts, and it's how the tests reach the production build.

### The tests (`e2e/`, Playwright, Chromium only)

2. **They run against the production build**: Playwright's `webServer` runs `npm run build` and then
   `vite preview` on a fixed port, and the tests open `/?e2e` on it. The viewport is 1280×720.
3. **Real input only.** Every action is a mouse move to the target, a check that the game reports
   the pointer is over that target (hover first; Phaser can miss a click that arrives without a
   pointer move), then a press and release. The tests never call scene methods or dispatch commands.
   They only *read* from the game: where things are drawn, and whether it's at rest.
4. **Positions come from the game.** A small helper (`e2e/game.ts`) reads the drawn objects through
   the hook: a hotspot's rectangle, an inventory slot, a verb coin button (by its icon), a dialogue
   option (by its text), a title or menu button (by its label). It converts game coordinates
   (1280×720) to page coordinates from the canvas's on-screen rectangle, so it works at any scale.
5. **Waiting is on game state, never fixed sleeps.** "At rest" means no effects playing (`busy` is
   false) and Dana isn't walking. While a line is showing, the test clicks to skip it, like an
   impatient player; that keeps the run fast and exercises the skip path. Slice 10's walks and pauses
   are covered by the same wait. Every wait has a timeout with a message saying what it was waiting
   for.
6. **Full play-through.** It computes the shortest solution the same way the always-winnable test
   does (step 9) and performs each step with clicks: a verb on a hotspot (hotspot → coin button, or
   straight through when there's only one verb), an item on a hotspot (slot → ✋ "Use with…" →
   hotspot), combining (slot → ✋ → the other slot), an item action (slot → its button), a dialogue
   option (click its line). After each step it checks the game state moved the way the core says it
   should (same room, inventory, and flags as `handle()` predicts), so a failure names the step.
   It ends by asserting the "To be continued…" card is showing.
7. **No console errors on a fresh load.** Open `/?e2e` with empty storage, wait for the title screen,
   click New game, wait for the room. No console errors, no uncaught page errors, no failed
   requests along the way.
8. **Save round trip.** Fresh storage → New game → the first few solution steps (enough to have an
   item and a flag) → at rest, so the autosave has run → reload → Continue → the game state is the
   same as before the reload.

### Shared search

9. The always-winnable test's search (`explore()` and its helpers) moves from
   `src/content/winnable.test.ts` into `src/content/explore.ts`, unchanged, plus a
   `shortestSolution(world, start)` that returns the commands of the first winning path. The
   always-winnable test imports it and stays green, printing the same walkthrough. It's pure TS, so
   the architecture test still applies.

### Scripts, CI, docs

10. `npm run test:e2e` runs Playwright. `npm test` (Vitest) is unchanged and doesn't pick up
    `e2e/` (Vitest only runs `src/**/*.test.ts`; Playwright files are `*.spec.ts`). `tsconfig`
    includes `e2e/` and `playwright.config.ts`, so `npm run typecheck` covers them.
11. **New workflow** `.github/workflows/e2e.yml` (its own file; `ci.yml` is unchanged), on the same
    triggers as CI (PRs to `main`, pushes to `main`), job name **"End-to-end (Playwright)"**:
    checkout → Node from `.nvmrc` with npm cache → `npm ci` → restore the Playwright browser cache
    (keyed by the installed Playwright version) → install Chromium (or only its system
    dependencies on a cache hit) → `npm run test:e2e`. On failure it uploads the Playwright report
    (screenshots, traces) as a run artifact. Same concurrency rule as CI. Action versions are the
    current majors, looked up when built.
12. **Required check: your call.** Making "End-to-end (Playwright)" a required status check on
    `main` is a repo settings change. I'll ask you once the workflow has run green on the PR.
13. `CLAUDE.md` Commands: `npm run test:e2e`, and that `?e2e` enables the hook in production builds.
    `.gitignore`: Playwright's output folders.

Out of scope: other browsers, mobile viewports, visual (screenshot) comparison, testing the
deployed site, running e2e in the Pages workflow, a test for every menu path (slot list, overwrite
prompt, settings): the round trip covers the save path.

## Acceptance checks

- `npm run test:e2e` passes locally, three tests, without fixed sleeps.
- `npm test`, `npm run typecheck`, `npm run build` pass; the always-winnable walkthrough is unchanged.
- **The e2e test can fail:** temporarily break a click target (e.g. aim at the wrong hotspot) and
  the play-through fails with a message naming the step; temporarily add a `console.error` on load
  and the console test fails. Both reverted.
- A production build without `?e2e` has no `window.__game` (checked in the browser pane).
- On the PR: both CI and the e2e workflow are green; a second run hits the browser cache.
- You decide whether to make the e2e check required.
